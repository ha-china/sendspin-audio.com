典型使用案例

每个案例都会说明其中涉及的角色、设备的连接方式、适合的配对方法，以及通常容易出问题的地方。请找到与你的产品最接近的案例，并在阅读分步章节之前先把它读完。

智能音箱或功放

角色：播放器（player）、控制器（controller）；如有线路输入，还可作为音源（source）。

  • 由服务器（server）发起连接；设备自行广播自己，家中的任何服务器都可以使用它。
  • 配对：没有显示屏时，通过音箱播报动态码；否则在显示屏上显示动态码。
  • 决定未配对访问（unpaired access）是否默认开启。对于普通音箱来说通常是开启的：用户期望能在应用中选中它并听到音乐。
  • 为端口之后的任何设备（例如外部功放）设置输出延迟，并让用户可以自行调整。
  • ESP32 设计可从 ESPHome 入手，其他情况则使用 sendspin-cpp。

流媒体播放器（仅输出）

角色：播放器；如果有遥控器或应用，还兼作控制器。

  • 网络流媒体播放器或 DIY 板子：自身不带音箱，向 DAC、功放或光纤输入供音。
  • 端口之后的 DAC、DSP 和功放会带来设备无法感知的延迟。测量一次，把它作为默认输出延迟出厂设置；并在设置中开放调整。
  • 配对：如果你有自己的应用，则在应用中显示动态码；否则使用印在设备上的静态码，在按下按键打开配对窗口的同时输入。大多数用户会使用访客模式（guest mode）。
  • 当硬件音量旋钮无法远程设置时，将其报告为只读。
  • Sendspin 可以与 AirPlay 和 Cast 共存在同一台设备上运行。当其他协议正在播放时，退出 Sendspin 组（group）但保持可用，这样用户随时可以用 Sendspin 把设备拿回来。只有当它不会让出时，才将其报告为不可用。

壁挂平板或显示屏

角色：元数据、封面图（artwork）、控制器；用于主题配色的颜色（color）；带音箱时还可作为播放器。

  • 按你实际渲染的像素尺寸请求封面图；服务器会替你完成缩放。用第二个通道获取模糊背景。
  • 定时元数据让你能在曲目切换之前就显示“接下来播放”。
  • 配对：在显示屏上显示动态码或二维码。
  • 控制器作用于显示屏所在的组。要为用户提供切换组的方式。
  • 基于 Web 的面板可从 sendspin-js 入手，嵌入式显示屏则使用 sendspin-cpp。

专用控制器

角色：仅作控制器。

  • 旋钮、按键面板、遥控器或语音卫星，控制所在房间，但自身不播放任何内容。
  • 它会接收所在组的状态，因此一圈 LED 可以显示音量和播放状态。
  • 在这类设备上，配对带来的麻烦通常得不偿失；经操作者（operator）批准的未配对访问才是常见选择。
  • 在队列为空时播放，会恢复该组上次播放的内容，因此单个按钮就足够了。

灯光与可视化设备

角色：可视化（visualizer）、颜色，或两者兼有。

  • 可视化帧与音频一样带有时间戳。运行时间滤波器，并在每帧对应的时间点渲染，而不是在到达时立即渲染。
  • 只请求你用得到的数据类型，并且以你能渲染的频率请求。不具备节拍检测能力的服务器可能没有节拍事件；峰值（peaks）则始终可用。
  • 颜色自带对比度保证，因此同一套调色板既可以驱动灯具，也可以驱动任何文字叠加层。

机顶盒或电视

角色：播放器、音源，可选内嵌服务器。

  • 作为播放器，它与音箱一起播放音乐。作为音源，它把电视音频送入系统，让房间的音箱来播放电影。
  • 在把电视音频发送给系统的同时，千万不要把它直接输出到本地音箱：本地输出会超前于网络。身兼音源和播放器的设备只播放服务器回传的内容。
  • 当用户切换到游戏主机或其他输入时，如果允许 Sendspin 被打断，则退出 Sendspin 组但保持可用；如果不允许被打断，则将播放器报告为不可用。无论哪种情况，服务器都会将其搁置一旁，绝不会自行把它拉回来。
  • 内嵌服务器让这台设备在没有家庭音乐服务器的情况下也能独立驱动整个房间。客户端与服务器模式如何共存，参见应用案例。

黑胶唱机、AUX 或蓝牙桥接器

角色：音源。

  • 设备负责采集音频、加上时间戳并发送。服务器负责重采样和混音。
  • 能检测到信号时就报告线路感应（line sense）；这样服务器可以在唱针落下时启动房间，在唱片结束时停止。
  • 使用来自时间滤波器的时间戳并包含漂移，而不只是偏移量，否则音频流会在一晚上逐渐跑偏。
  • 网络卡顿之后，丢弃积压的数据，从实时采集处恢复播放，而不是把旧音频一次性突发发送出来。
  • 音源始终需要在服务器上获得操作者的明确批准，而带麦克风的设备出厂时应默认关闭未配对访问。

桌面或移动应用

角色：作为客户端时是播放器和控制器；当应用自己播放时，则是完整的服务器。

  • 空闲时，应用是一个客户端：它会显示为 Music Assistant 或家中任何其他服务器的目标设备。
  • 当用户在应用中开始播放时，应用会变成服务器并向其他音箱发送音频。用原因 another_server 向你之前作为客户端所连接的服务器告别，并同时广播 _sendspin-server._tcp，让以客户端方式发起连接的设备也能找到你。
  • 按照惯例，客户端监听 8928 端口，服务器监听 8927 端口，因此两者可以运行在同一台机器上。

软件播放器或音乐服务器

角色：服务器、客户端，或两者兼有。

  • 软件音乐播放器、Linux 音频盒子、家庭自动化中枢：添加服务器端以把它的输出发送到 Sendspin 设备，添加客户端侧以作为其他服务器的目标设备，或者两者都做。
  • 如果你使用 Python，可复用 aiosendspin；它就是 Music Assistant 内部的服务器。
  • 你的服务器身份密钥必须在备份和迁移之后保持不变，否则每台设备都会把恢复出来的服务器当作陌生人。
  • 服务器 UX 章节涵盖了发现、批准和配对。

一个家中有多台服务器

角色：任意；这里讲的是共存问题。

  • Music Assistant、手机应用和机顶盒可以同时作为服务器。服务器发起的连接让这一切无需配置即可实现。
  • 一个客户端只持有一条播放连接。开始播放的服务器会接管这条连接；失去连接的服务器会收到 another_server，继续把设备显示为可用，并且不会陷入循环重连。
  • 每台服务器分别进行配对。客户端至少要存储五条配对记录。
  • 在你的服务器界面中，把这种交接显示为“正在从别处播放”。

#选择连接模式

除非你有不这样做的理由，否则应使用服务器发起的连接。客户端自行广播自己，服务器能够发现它，并且上文的 多服务器规则已经对此做出了定义。客户端发起的连接是为脚本、测试工具以及自带服务器选择器的软件而存在的；当出现两台服务器时会发生什么，就由你自己决定了。

#选择配对方法

你的设备具备 应提供
有显示屏 动态配对码，同时以数字和二维码两种形式呈现
有音箱但没有显示屏 动态配对码，通过语音播报
有专属应用 在应用中显示的动态配对码，应用充当设备的显示屏
以上都不具备 印在设备上的静态配对码，在通过按键、针孔或特定断电重启方式打开配对窗口时输入
所在平台已经认识该设备 由平台把设备的配对 PSK 交给服务器，就像 Home Assistant 对 ESPHome 设备所做的那样

只提供一种基于码的方式，而不是两种都提供，这样用户就不必在两者之间做选择。每个客户端也会实现配对 PSK 方法，用于系统之间的自动交接。开启了访客模式的音箱可以为操作者批准的任何服务器播放，因此许多用户根本无需配对。详情请参阅客户端配对章节。
